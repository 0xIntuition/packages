# 6. The `gen1` derived scheme

---

## 6.1 Purpose and honest framing

`gen1` is the Class C scheme: the identifier used when no registry covers an entity and it has no natural key. It hashes a small, deliberately chosen set of the entity's own attributes.

Before the algorithm, its limitation, stated plainly:

> **A `gen1` identifier does not identify an entity. It identifies the facts it was derived from.**

`int:gen1:music-group:r4:…` derived from the name "Nirvana" identifies *the name-level concept "Nirvana", understood as a music group*. Every band by that name maps to it. That is not a defect in the algorithm; it is an accurate report of what the minter knew ([§0.3](./00-overview.md), tenet 2).

Everything below — the classification namespace, the visible rung tag, the mandatory P1 profile — exists to keep this limitation **visible** rather than concealed behind an opaque hash.

## 6.2 Value format

```abnf
gen1-value = slug ":" "r" tag ":" hash16

slug   = 1*( %x61-7A / DIGIT / "-" )     ; the entity type's slug
tag    = %x31-39 *DIGIT                   ; stable rung tag, >= 1, no leading zero
hash16 = 32( %x30-39 / %x61-66 )          ; 32 lowercase hex chars = 16 bytes
```

A complete IID:

```text
int:gen1:movie:r4:fb681afe7d438cad73ae90a70f1cc55a
     │     │    │   │
     │     │    │   └── first 16 bytes of keccak-256 over the preimage
     │     │    └────── stable rung tag: recipe r4 produced this
     │     └─────────── entity type slug
     └───────────────── scheme: derived, version 1 of the normalization algorithm
```

Note that the value contains two colons, so a parser splitting on all colons will mis-handle it ([§2.3](./02-grammar.md)).

### Why each part is present

| Part | Purpose |
| :-- | :-- |
| `gen1` | Carries the **normalization-algorithm version**. Normalization will eventually improve; without a version in the identifier, every improvement silently forks every derived identifier ever produced. `gen2` may later coexist with `gen1`, bridged by equivalence. |
| slug | Namespaces the hash space per entity type, and tells a reader which family of recipes produced this. A movie and a product with the same name do not collide. |
| `r<N>` | Makes the producing recipe inspectable without re-derivation. Given the identifier alone, you can look up exactly which fields were hashed. |
| `hash16` | 128 bits. Collision probability is negligible at any plausible corpus size; keccak-256 matches the surrounding Intuition toolchain. |

## 6.3 Derivation

### Step 1 — Resolve the recipe fields

Take the field set named by the rung. Every field MUST resolve to a non-empty value after `NORM-1` ([§4](./04-normalization.md)). If any does not, the rung does not fire and derivation falls to the next rung ([§5.2](./05-identity-ladders.md)).

Recipes name **scalar fields only**. Arrays, objects, booleans, and nulls MUST NOT appear.

### Step 2 — Normalize each value

Apply `NORM-1` to each string value. Dates and numbers are canonicalized per [§4.5](./04-normalization.md).

### Step 3 — Build the preimage

The preimage is the UTF-8 encoding of this exact JSON structure:

```json
{"c":"<slug>","f":{"<key>":"<normalized value>",...}}
```

Requirements:

1. Exactly two top-level keys, in this order: `c` then `f`.
2. Keys inside `f` sorted lexicographically by **UTF-16 code-unit order** (the ordering produced by a plain string sort in the reference implementation).
3. **No whitespace anywhere** — no spaces after colons or commas, no newlines.
4. String escaping per [RFC 8785 (JCS)](https://www.rfc-editor.org/rfc/rfc8785) rules.
5. `f` MUST contain **only** the fields named by the rung. Never the entity's full field set — descriptive fields such as descriptions, keywords, or image URLs MUST NOT leak into identity, because they vary between sources for one entity.
6. `f` MUST contain at least one field.

### Step 4 — Hash

Compute keccak-256 over the preimage bytes. Take the **first 16 bytes**. Render as lowercase hexadecimal without a `0x` prefix.

### Step 5 — Assemble

```text
"int:gen1:" + slug + ":r" + tag + ":" + hash16
```

**The rung tag is not part of the preimage.** It annotates the identifier; it does not affect the hash. Two recipes over the same fields for the same entity type would produce the same hash with different tags — which is why tags are assigned per recipe and never reused ([§6.4](#64-stable-rung-tags)).

## 6.4 Stable rung tags

> **A rung tag is a frozen recipe identifier, not a ladder position.**

When a recipe is created it receives the next unused tag for that entity type. That tag is permanent.

Inserting a new recipe into the middle of a ladder assigns it a **fresh** tag and changes only the declaration order — it never renumbers existing tags. Consequently, tags in a ladder need not be contiguous or ascending, and an identifier bearing `r4` always refers to the same field set for the lifetime of the entity type.

The alternative — tags as positions — would mean that adding a recipe silently changes the meaning of every previously issued identifier, making the visible tag actively misleading. That is worse than having no tag at all.

## 6.5 Worked example

Deriving the `movie` rung `r4`, whose recipe is `{name, yearPublished}`, for *Inception*:

```text
Input fields
  name           "Inception"
  yearPublished  "2010"

Step 2 — NORM-1
  name           "Inception"  →  "inception"
  yearPublished  "2010"       →  "2010"

Step 3 — preimage (no whitespace, keys sorted: "name" < "yearPublished")
  {"c":"movie","f":{"name":"inception","yearPublished":"2010"}}

Step 4 — keccak-256, first 16 bytes
  fb681afe7d438cad73ae90a70f1cc55a

Step 5 — assemble  (tag r4, not hashed)
  int:gen1:movie:r4:fb681afe7d438cad73ae90a70f1cc55a
```

The release year stays in the recipe because it is an intrinsic stable scalar and remakes are pervasive: *Dune* (1984) and *Dune* (2021) are different films, not formatting variants of one title. The director does **not** appear, because a director is a related entity ([§0.3](./00-overview.md), tenet 3) — that fact travels as a claim.

## 6.6 Mandatory P1 representation

> **A `gen1` identifier MUST NOT be minted as a bare P0 anchor.**

Class C atoms floor at profile P1 ([§7](./07-representation-profiles.md)): the atom payload MUST include the recipe fields alongside the identifier.

Two reasons, both load-bearing:

1. **Verifiability.** The recipe fields *are* the hash's preimage evidence. Without them the identifier is an unverifiable 128-bit string — nobody can check that it was derived correctly, and nobody can re-derive it.
2. **Renderability.** A bare `gen1` string is not displayable. There is nothing for a user to read.

Class A and B anchors do not have this problem: their values are meaningful in themselves and resolvable against an external authority.

## 6.7 Collision characteristics

Two distinct kinds of collision, with very different meanings:

| Kind | Cause | Probability | Correct response |
| :-- | :-- | :-- | :-- |
| **Semantic** | Two different entities genuinely share the recipe's facts — two bands named Nirvana | Common, and **intended** | None. The identifier is correct. Resolve by climbing to a stronger rung as facts improve. |
| **Cryptographic** | Two different preimages hash to the same 16 bytes | ~1 in 2⁶⁴ at 2³² entities per entity type | Would be a defect. Not expected to occur. |

Implementations MUST NOT attempt to detect or repair semantic collisions by mutating the identifier. Appending a counter, a source name, or a timestamp destroys determinism — the same entity would receive a different identifier on every import — to conceal a limitation that the specification deliberately makes visible.

## 6.8 Versioning `gen1`

`gen1` is frozen: its preimage construction, hash function, truncation length, and `NORM-1` dependency will not change.

A future improvement to normalization ships as `NORM-2` with a companion `gen2` scheme. Both then coexist in the registry, identifiers under each remain valid and stable, and atoms carrying `gen1` and `gen2` identifiers for the same entity are joined by the equivalence layer exactly as any other pair would be. Nothing is re-minted and nothing is invalidated.
